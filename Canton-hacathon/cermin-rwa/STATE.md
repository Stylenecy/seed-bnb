## 4. Lessons learned (mistakes caught by review — do not repeat)

- **Idempotency must be tested where the gate actually bites** — the "no double-fire" test originally passed via an earlier short-circuit, not the tracked-contractId gate; the real scenario is a CAPPED repay leaving ratio < trigger.
- **Per-item error isolation in loops touching money**: one throwing loan/coupon exercise must not skip the rest of the poll; wrap each iteration, keep idempotency state writes AFTER the awaited exercise.
- **JSON Ledger API returns Decimals AND Ints as strings** — coerce numerics at the seam (`NUMERIC_FIELDS`/`coerceNumerics`); typing them `number` compiled fine and broke only live.
- **JWT `ledgerId` must be `sandbox`** on `daml start` (2.x); wrong value silently returns 0 rows — no error.
- **Same-cycle staleness:** GuardRepay archives+recreates the Loan; a sweep later in the same poll must re-resolve the loan cid (`resolveWitnessesForLoan`) — never reuse the snapshot cid after a write.
- **Every fetched cid in a guardAgent-controlled Daml choice must be pinned** (borrower/guardAgent/instrumentId equality asserts) — the reviewer hunts substitution holes; pinning made GuardRepay/SweepToLoan provably narrow.
- **0fr/max-height disclosure keeps content tabbable** — collapsed expandable content needs `inert` (React 19 prop) or it's a keyboard trap.
- **"Single source of truth" constants must actually be imported** — DEFAULT_STRATEGY_ID existed and was tested but unwired; behavior matched by coincidence. Wire + add a drift-guard test.
- **Runbooks must be written against the shipped UI, not the intended one** — Mode A step 4 described controls that didn't exist; the fix was wiring the UI, but the lesson is verify runbook steps clickable end-to-end.
- **daml test discovers every top-level Script as a test** — name shared fixtures accordingly or accept noise.
- **Docs drift is a real reviewer catch**: README "no code yet", thresholds 150% vs shipped 145% — update docs in the same pass as the behavior change.
- **Verify exact version pins by installing/hitting the API, never trust a version number in a brief at face value** — "Daml SDK 3.5.2" doesn't exist (conflated with Canton binary 3.5.6); `daml install <ver>` / `gh api .../releases/tags/<ver>` catches this in seconds.
- **Canton 3 removed party display names entirely** — `PartyDetails` is `{party, isLocal}` only; any live-ledger "find this party by name" code must match `partyToText` == hint OR `isPrefixOf (hint <> "::")` (party IDs are `hint::fingerprint`) — NEVER a bare prefix, which makes "Borrower" also match "Borrower2" (reviewer catch; see `matchesPartyHint` in Demo.daml).
- **A parallel-fanout read races a lazily-cached token** — an OAuth2 provider that only checks-then-fetches mints N tokens when N reads start on a cold cache (`getPosition` fans out 5). Guard the fetch with an in-flight promise (first caller starts it, the rest await it, clear on settle), not just the cached-value check.
- **A store field with no ledger source silently disables live UI** — the vault top-up gated its button on a mock `wallet.balance` the live `applyPosition` never sets (stays 0), so `Add` was always disabled on DevNet. Any control gated on a mock-only field must relax that gate under `isBackendMode()`. Same class as a mode-blind badge that lied ("Mock data" on a live ledger).
- **Fixed demo affordances go stale as ledger state drifts** — the "$0.76" rescue button assumed the fresh-scene outstanding (~6000); after real rescues shrank it, $0.76 no longer breaches. Live demos must compute the trigger input from current state (breach price = `1.30 × outstanding ÷ 10000`), and mind hard UI floors (slider min $0.50 caps how many times the loop repeats before a re-seed).
- **An agent-local idempotency key that isn't per-entity silently drops entities in a multi-tenant world** — the "already acted on this price cid" guard keyed by `loanId` alone worked for one borrower, but every self-service borrower shares loanId `loan-1` AND the one global PriceFeed cid, so the first borrower's rescue marked the cid "acted" and skipped all the rest — no error, just missing rescues. Key idempotency (and grace/witness dedup) by the FULL entity identity (`borrower + loanId`), and hunt for `list[0]`/single-key fallbacks the moment scope goes from one tenant to many. (Task 16.)
- **Filming/screenshotting a wizard means staging EVERY step** — a fullPage screenshot of `#/app/borrow` only captures step 0; the strategy cards live behind a "Next" click, and the video's flagship "named strategies" shot shipped with the wrong screen until review caught it. Script the click-through per state, then eyeball each PNG before compositing. (Related orchestrator repeat-offense: a `cd` in one Bash call persists into the next — a relative `ls .superpowers` from `video/` "proved" the ledger was wiped when it wasn't. Absolute paths, always.)
- **The shared DevNet OAuth user's explicit `CanActAs` grants are NOT permanent — they can silently disappear days later, even though contract state and party allocation are untouched.** Task 22 (5 days after Task 16) hit a `403 "A security-sensitive error has been received"` on `/api/faucet` for a brand-new self-service party. Reads still worked (blanket `CanReadAsAnyParty` on the shared ParticipantAdmin user), and the NEW party's own fresh grant was visibly present — but `cermin-issuer`/`cermin-pool-operator`/etc.'s explicit `CanActAs` grants from Task 14–16 were gone from the live rights list entirely, most likely evicted by a rights-count cap shared across every hackathon team using the SAME `validator-devnet-m2m` identity (the rights list is a flat, unpaginated array mixing dozens of other teams' party hints). Fix is one idempotent command, safe to re-run any time this happens again: `node scripts/seed-ledger.mjs` (no subcommand) — it re-grants CanActAs/CanReadAs for all 5 fixed parties and safely skips scene creation if a Loan is already live. **Lesson: on this shared sandbox, a stale "it worked before" is not evidence it works now — re-run the grant step (or check `GET /v2/users/<id>/rights` for your fixed parties) before trusting a write path that hasn't been exercised in days.**
- **A high fan-out of concurrent ledger reads is both an etiquette problem and a fragility problem** — `getPosition`/one poll opening ~12 simultaneous HTTPS connections to a SHARED validator is impolite AND chokes a constrained network path (measured ceiling ~3 concurrent in the agent sandbox; undici not importable to tune the pool). Cap it in the seam (`ConcurrencyLimiter` + `LEDGER_MAX_CONCURRENCY`) and retry once on a transient throw. Also: detached background processes lose this environment's network exemption — a live-ledger proof must run its services as live children of ONE unsandboxed call, not as `nohup … & disown`. (Task 16.)
